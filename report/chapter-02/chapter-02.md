# บทที่ 2 ความต้องการและงานที่เกี่ยวข้อง

## 2.1 กลุ่มผู้ใช้และลักษณะการใช้งาน

ผู้ใช้หลักคือผู้ฝึกหรือผู้ทดสอบที่ต้องการดูข้อมูลระหว่างออกกำลังกาย ผู้ใช้เริ่มจากหน้าเว็บ ตรวจสอบความพร้อมและสถานะเซนเซอร์ จากนั้นเริ่มเซต ดูค่าที่เปลี่ยนแบบสด และหยุดเซตเพื่อดูสรุปผล

ผู้พัฒนาหรือผู้ดูแลระบบเป็นผู้ใช้อีกกลุ่มหนึ่ง ต้องตั้งค่า Wi-Fi, URL ของเว็บ, การเชื่อมต่อ I2C/UART, MongoDB และค่า secret ของ backend รวมถึงตรวจสอบ log เมื่ออุปกรณ์ไม่เชื่อมต่อ

ลักษณะการใช้งานเป็นระบบอุปกรณ์เดียวที่ส่งข้อมูลเข้าสู่เว็บในขณะฝึก โดย frontend มีการป้องกันการบันทึกพร้อมกันของผู้ใช้ต่างคนบน telemetry store ที่เป็นหน่วยความจำร่วมของเซิร์ฟเวอร์

## 2.2 ข้อมูลที่ระบบรับเข้า ประมวลผล และแสดงผล

### ข้อมูลรับเข้า

- Uno ส่งค่า `emg,fsr` เป็นข้อความทาง UART
- ESP32 รับค่าจาก Uno และอ่าน MPU, MAX30102, MLX90614 ผ่าน I2C
- ESP32 ส่ง JSON telemetry ที่มี `emg`, `fsr`, `mpu`, `vitals`, `device`, `timestamp` และสถานะปุ่ม
- เว็บรับข้อมูล JSON จากอุปกรณ์ และรับคำสั่งจากผู้ใช้ เช่น เริ่ม/หยุดบันทึกและบันทึก calibration

### ข้อมูลประมวลผล

ESP32 คำนวณ pitch, roll, velocity, ความนิ่งของ FSR, HR และ SpO2 ประมาณการ ส่วน frontend แปลง ADC เป็นหน่วยที่ใช้แสดงผล คำนวณ MVC percent และสถานะ high tension รวมทั้งใช้ MediaPipe/OpenCV ช่วยวิเคราะห์การเคลื่อนไหว

### ข้อมูลแสดงผลและบันทึก

แดชบอร์ดแสดงกราฟ EMG ค่าแรงและความนิ่งของ FSR การเคลื่อนไหว สัญญาณชีพ สถานะอุปกรณ์ จำนวนครั้ง และผลรายเซต ข้อมูลผลเซตและ calibration ส่งต่อ FastAPI เพื่อจัดเก็บใน MongoDB

## 2.3 ความต้องการด้านการทำงานและข้อกำหนดอื่นของระบบ

### ความต้องการด้านการทำงาน

1. อ่านค่าเซนเซอร์และส่งข้อมูลต่อเนื่องตามรอบที่กำหนด
2. รับ telemetry จาก ESP32 และแสดงผลสดผ่าน SSE
3. เริ่มและหยุดการบันทึกตามเซสชัน พร้อมจำกัดการบันทึกไม่ให้ข้ามผู้ใช้
4. ปรับเทียบค่า EMG และ FSR แบบผูกกับผู้ใช้
5. ลงทะเบียน เข้าสู่ระบบ ต่ออายุ token และตรวจสอบสิทธิ์ก่อนใช้ข้อมูลส่วนตัว
6. บันทึกผลรายเซตและค้นผลย้อนหลังตามผู้ใช้หรือ session id

### ข้อกำหนดอื่น

- UART ระหว่าง Uno กับ ESP32 ต้องใช้ baud rate และระดับแรงดันที่ถูกต้อง
- I2C ต้องใช้ขา SDA/SCL และ address ตามการต่อจริง
- การทำงานที่มีเวลาคงที่ควรไม่ถูกบล็อกจาก HTTP หรือการแสดงผล
- ต้องมีการตรวจสอบข้อมูลผิดรูปแบบและรับมือการเชื่อมต่อหลุด
- ค่าที่เป็นค่าประมาณต้องระบุข้อจำกัดก่อนนำไปตีความ

## 2.4 แนวคิด เครื่องมือ หรืองานที่เกี่ยวข้อง

แนวคิดสำคัญที่ใช้ในระบบคือการแบ่งงานตามความเหมาะสมของอุปกรณ์ ได้แก่ interrupt และ timer สำหรับงานที่ต้องตรงเวลา, FreeRTOS task สำหรับแยกงานบน ESP32, UART สำหรับลิงก์ระหว่างบอร์ด, I2C สำหรับเซนเซอร์หลายตัวบนบัสร่วม และ HTTP/SSE สำหรับส่งข้อมูลระหว่างอุปกรณ์กับเว็บ

เครื่องมือและเทคโนโลยีที่ปรากฏในแหล่งข้อมูล ได้แก่ Arduino framework, FastAPI, SvelteKit, TypeScript, MongoDB, Docker และไลบรารีของเซนเซอร์ เช่น `Adafruit_MLX90614`, MAX30105/heart-rate และ `LiquidCrystal_I2C`

ส่วนการวิเคราะห์กล้องใช้ MediaPipe ในตัวนับหลัก และมี OpenCV.js เป็นตัวนับตรวจสอบแบบ motion difference แยกต่างหาก โดยตัวนับ OpenCV ไม่เรียกบันทึก rep หลักซ้ำ
